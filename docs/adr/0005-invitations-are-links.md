# 0005 — Invitations are links, and a second auth instance creates the account

Date: 2026-09-22
Status: accepted

## Context

Until M6 there was no way to add a person to a workspace. The seed created one admin, and
everybody after them was added by an operator writing a `member` row by hand. The
`invitation` table Better Auth generates had existed since the first migration with no code
reading or writing it.

Two things stood in the way of the obvious implementation.

**There is no mail transport.** Nothing in this product sends email. Adding one is not a
line of code: it is a provider account, a sending domain, SPF and DKIM records,
deliverability that has to be watched rather than assumed, a queue so a slow SMTP call does
not sit inside a request, and a story for what happens when a message bounces. All of that
before the first colleague can be invited to a pilot that runs on one tenant.

**Sign-up is disabled, on purpose.** `emailAndPassword.disableSignUp` is what makes the
product invite-only: there is no route anybody can post to and come out holding an account.
But accepting an invitation has to create one.

## Decision

**The link is the credential, and the admin delivers it.** The console shows the link once,
with an instruction to copy it and send it however they already talk to that person. The
same mechanism issues a password reset for somebody locked out, because it answers the same
question: this address, one action, once, before this time.

Only the SHA-256 hash of the token is stored. A database that can hand back working
invitation links is a database that can let somebody into a tenant, which is the same
reasoning that encrypts every other credential here. The token is 256 bits from the CSPRNG,
single-use, and spent in the statement that checks it, so two people opening the same link
cannot both be let in.

**A second auth instance creates the account.** `createAuth(db, { allowSignUp: true })` is
built at startup, kept on the API context, and never passed to the route handler. Better
Auth checks `disableSignUp` inside its own handler, per instance, so the capability exists
at exactly one call site — the accept route, which has already proved the caller holds a
valid unspent token. Both instances share the secret and the database, so the session cookie
one mints is an ordinary session to the other.

**Spending the token and writing the membership share a transaction.** Apart, a failure
between them leaves a person with an account, no membership, and a link that will never work
again: the one outcome with no way out but an admin issuing another.

The account is created *before* the token is spent, deliberately, and that ordering is the
opposite way round. Better Auth owns that write and cannot join our transaction, so if it
fails — a password it will not accept, an address that raced us — the invitation is still
unspent and the person simply tries again. The reverse order would burn the link on every
rejected password.

## Consequences

An invitation can be forwarded. Whoever holds the link can use it, and the address on the
invitation is the one the account is created for, so a forwarded link creates an account at
an address its recipient may not control. This is accepted: the admin chose who to send it
to, the link expires in seven days, and the alternative is the mail transport above. An
existing account is safer — that path requires a signed-in session whose address matches.

A reset link is issued by an admin rather than requested by the person who lost their
password. Without a mail transport there is nothing to prove an address with, so the admin
is the one deciding that the person asking really is the person. They are better placed to
make that judgement than a mail server is.

Nothing is auditable about delivery. We know a link was issued and when it was spent; we do
not know where it went. Both are written to the workspace's `audit_log`.

Better Auth's own `invitation` table stays unused and unmodified. It assumes a
`sendInvitationEmail` hook, an acceptor who is already signed in, and it stores its id in
the clear as the credential. It is regenerated by `bun run auth:generate`, so leaving it
alone costs nothing.

## Alternatives considered

**Email, properly.** The right answer eventually, and the wrong thing to build first. It
can be added later without changing the token, the table or the accept route: only who
transports the link changes.

**An admin sets a temporary password.** Simpler, and it puts a password into whatever chat
the admin uses, where it stays. It also needs a change-password screen before anybody can
stop using the temporary one, and somebody locked out has no path at all except being
deleted and recreated, which strips their name from every message they ever sent.

**Flipping `disableSignUp` at runtime.** A single mounted instance whose behaviour depends
on a flag is one mistake away from a public sign-up route. A capability that exists only
where it is used cannot be reached by a route that forgot to check.
